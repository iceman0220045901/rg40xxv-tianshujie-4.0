# 移植问题与解决办法

按"现象 → 真因 → 做法"记，包含走过的弯路，避免重复踩。

## 1. 花屏：纵向条纹 / 半屏错位

**现象**：从 Ports 菜单启动后画面是彩色纵向条纹，或只有半屏有内容。

**真因**：前端 `muos2.bin` 在跑和退出后，fb 模式不一样。

- 前端在跑：`16bpp`
- 前端退出、进 Ports：`32bpp`、`stride=2560`、`virtual=640×960`、`rgb=16/8 8/8 0/8`

引擎原来按 16bpp 写，一进 Ports 就全错位。

**做法**：`patch_fbmode.py` —— 在 `JY_FbBlit` 的 5 秒心跳里重新 `ioctl` 读一遍 bpp/stride/RGB，发现变化就刷新 `g_FbBpp / g_FbBytes / g_FbStride / g_PixRPos`，并写一行日志 `fbdev: mode changed`。

顺带一个坑：**前端还在跑（fb 16bpp）时直接起引擎，进程会被 `Killed`，日志一行没有**。必须先让前端退出再起。

## 2. SDL2 选哪一份

**现象**：换成系统默认的 2.28.5，全屏 blit 慢到 21 ms；换成机器自带 2.0.12 直接降到 5.34 ms。

**做法**：写了个最小基准程序（dummy 视频驱动，1280→1280 全屏 blit 取 20 次均值），把机上能拿到的几份库都测一遍：

| 库 | 全屏 1280→1280 |
|---|---|
| 自带 2.0.12（4,965,488 B） | **5.34 ms** |
| 自编译 2.0.12 -O3（1,432,240 B） | 5.80 ms |
| 系统 2.28.5（2,764,840 B） | 21.16 ms |

结论：版本差异（4 倍）值得换，**同版本自编译不值得**（SDL blit 内层已经手写优化，`-O3 -mtune=cortex-a53` 只会加重 i-cache）。

部署方式：把 2.0.12 拷进 `lib/`，靠 `LD_LIBRARY_PATH=$PWD/lib:...` 和 `-Wl,-rpath,'$ORIGIN/lib'` 优先加载。

## 3. 输出缩放占了太多帧时间

**现象**：1280×720 缩到 640×360，每帧 8~11 ms。

**做法**：`patch_scale2x.py` —— 只对"精确 2:1 + 32bpp"这一种情形开快路径（`g_FbBytes==4 && srcW==dstW*2 && srcH==dstH*2`），每轮 3 条 NEON 指令出 2 个输出像素：`vld1q_u8 ×2` → `vhaddq_u8` → `vuzp_u32` → `vhadd_u8` → `vst1_u32`。误差上限 1 色阶；`dstW` 为奇数时最后一个像素回落原公式。

结果：标题页 29.0 → **37.4 fps**，游戏内 13.8~16.4 → **20.6~20.8 fps**。

## 4. 每帧把整屏从零重画

**现象**：换更快的 SDL2 之后帧率还是上不去，CPU 单核已满。

**怎么查的**：写 `LD_PRELOAD` 探针，hook `SDL_UpperBlit / SDL_UpperBlitScaled / SDL_FillRect / LockSurface / UnlockSurface / UpdateWindowSurface / PollEvent`，每 3 秒覆盖写一次统计。注意**探针和 `stdbuf -oL` 不能同时用，同时用进程会被 SIGKILL、日志只留一行 `Killed`**。

实测结果：

| 场景 | blit 次数/帧 | blit 耗时/帧 | 占帧时间 | 单次 blit |
|---|---|---|---|---|
| 标题页 | 17 | 9.9 ms | 37% | 0.585 ms |
| 读档列表 | 49 | 56.7 ms | 68% | 0.78 ms |
| 游戏内 | **1405** | **23.0 ms** | **48%** | **0.016 ms** |

单次只有 0.016 ms、次数却有 1405 —— 瓶颈是"次数 × 固定开销"，不是拷贝速度。这解释了为什么换更快 / 自编译 SDL2 都没收益。

同时还量了引擎手写像素的时间（`LockSurface → UnlockSurface` 区间）：152 秒里只有 81.6 ms，占 0.05%，说明绘制几乎全是 blit。

**做法**：给场景层函数套整屏缓存（`patch_smapcache.py` / `patch_mmapcache.py`）：把原函数改名 `_raw`，外面套同名包装，缓存键取镜头坐标、角色朝向、裁剪矩形（室内再加场景号和偏移），命中就一次满屏贴，未命中调 `_raw` 画完再把裁剪区抄进缓存 surface。屏幕旋转一律回落 `_raw`。

结果：客栈 20.8 → **29.8~30 fps**，大地图约 18 → **26.0~26.4 fps**，走动时 23~27 fps（每步重建）。

## 5. 编译参数

设备上试过 `-O3 -mcpu=cortex-a53 -mtune=cortex-a53 -fomit-frame-pointer`：标题 37.4（与 O2 相同）、游戏内 21.1 对 20.6 fps，落在噪声内。老代码怕严格别名，收益又为零，回退到 `-O2`。

**踩过的坑**：本地 `build.sh` 已改回 `-O2`，但设备 `/tmp` 里那棵树还是旧的 `-O3` 脚本，用它编出来的引擎比无缓存版大 52 KB（519,832 vs 467,448 B），明显异常。同步回 `-O2` 后体积正常（471,968 B，+4.5 KB 正好是缓存那段代码），帧率完全一样。**体积异常先查编译参数有没有同步。**

## 6. MIDI 没声音

**现象**：文件路径对、音色库对、日志无报错，就是不出声。

**真因**：两处叠加 —— 用了错误的解码入口（该用 `StreamCreateFile` 的分支走了别的），以及音色库开关没挂上（`CONFIG.MP3=1` 时会去找不存在的 `.mp3`，插件初始化失败顺带把音色库也带没了）。

**做法**：改回 MIDI 解码入口，`CONFIG.MP3=0`。

## 7. 音量：一开就最大声、机身音量键无效

**澄清**：不是"没声音"，是**音量降不下来**。

**真因两条**：

1. `/etc/asound.conf` 里 `pcm.!default` 是 `type hooks`，`ctl_elems` 把 `digital volume` 直接写成 **63** 并 `lock true`。于是每次打开设备都被强制满音量，`amixer cset numid=2 40` 直接报 `Operation not permitted`。真正可写的只有 **`lineout volume`（numid=3，0~31，dB 0 → −43.5）**。
2. 音量键本来由前端 `muos2.bin` 读，跑 Ports 游戏时前端已经退出，所以按键没人处理。

**做法**：

- 新增 `volkey.py`：不 grab 设备（与 gptokeyb 共存），监听音量键，调 `lineout volume`，起始 18/31、步长 2，值存 `/tmp/jy4_dac_vol`。
- `patch_vol.py`：`PlayMIDI()` 每次播曲都会用 `getenv("JY_MUSIC_VOL")` 覆盖游戏内设置（`JY_PlayWAV()` 同理），`launch.sh` 里写死的 50/40 会把游戏内音量设置盖掉。改成统一的增益函数 `JY_VolEff()`，音乐 `JY_VOL_GAIN=2.5`、音效 `JY_SFX_GAIN=4`。

## 8. Ports 菜单里看不到项目

**真因**：这个前端**不读 `/mnt/mmc`，也不读 `config.json`**。真实扫描目录是 **`/mnt/sdcard/Roms/PORTS`**，每一条是 `名字.sh`，图标放同级的 `Imgs/名字.png`。

**做法**：建 `/mnt/sdcard/Roms/PORTS/天书劫4.0.sh`（`#!/sh`，**刻意不 source PortMaster 的 `control.txt`** —— 那是 bash 专用，而前端用 sh 执行，混用直接语法错）+ `Imgs/天书劫4.0.png`。

`launch.sh` 里另外两件事：

- 沿 PPID 上查最多 6 层 `comm`，命中 `muos` / `dmenu` / `MainUI` 就设 `FROM_FRONT=1`
- 单实例守卫：起跑前 `kill -9` 残留的 `jysdllua` / `gptokeyb` / `volkey.py`（用 pid 文件版，别用 `ps | grep | awk` 的循环，会把发起它的 shell 一起杀掉）

## 9. 电源键待机，"一亮就睡回去"

**能做的前提**：4.9 内核没有 `/sys/class/wakeup`，输入设备也没有 `power/wakeup`，没法用 sysfs 注册唤醒源；RTC `wakealarm` 可写但实测叫不醒 mem。但**短按电源键能唤醒 mem**（PMIC 层面），所以功能成立。

系统原生 `/mnt/vendor/ctrl/pwr_new.sh` 的做法就是 `echo -n mem > /sys/power/state`。

**bug**：唤醒的那一次按键被旧守护当成新的待机请求，屏幕一亮立刻又睡回去。

**修复思路**：用墙钟与单调时钟的漂移量判定"系统刚从待机里出来"（`DRIFT_MIN=2.0`），给出 `WAKE_GUARD=6.0` 秒的唤醒保护窗口；同时 `drain()` 排空事件队列、`pressed_at.clear()` 清按键记录；长按超过 `LONG_PRESS=2.0` 忽略。

## 10. 抓帧取证

设备上抓 fb 要按 stride 取，不是按宽度：

```
dd if=/dev/fb0 of=/tmp/x.bin bs=2560 count=480     # 1,228,800 B，正确
dd if=/dev/fb0 of=/tmp/x.bin bs=1280 count=480     # 只有半帧，错
```

本地再用 `raw2png32.py <raw> 640 480 2560 bgra <png>` 转 PNG。

## 11. 按键注入的坑

- uinput 设备结构长度试出来**只有 1116 字节可用**，1112 字节、`UI_DEV_SETUP` 都恒 `EINVAL`。
- **多个残留的注入进程会同时持有 `/dev/uinput`，后续写入被阻塞**，日志只打一行 `sent DOWN` 然后挂死。正确姿势是先清干净，再每次一个键、单独进程、带 `timeout`。
- 用 `pgrep -f xxx | head -1` 配合 `kill` 会匹配到发起命令的 shell 自己，把会话杀掉；用 `pidof` 或精确进程名。
