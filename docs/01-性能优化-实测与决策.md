# 性能优化记录：SDL2 库版本与 NEON 缩放快路径

日期：2026-11-11
设备：Anbernic RG40XXV（Allwinner H700 / sun50iw9，4×Cortex-A53 @1.512GHz，governor=performance，glibc 2.35，kernel 4.9.170）
画面链路：引擎内部 1280×720 32bpp surface → 自绘 fbdev 后端 → 面板 640×480 32bpp（stride 2560），2:1 缩小后 640×360 居中，上下各 60px 黑边。

## 结论（一句话）

真正把帧率抬上去的是**把每帧的 2:1 缩放从通用盒式滤波换成 NEON 快路径**；换 SDL2 库版本（2.28.5 → 2.0.12）是另一件已生效的事，但**自编译优化版 SDL2 没有收益，已否决**。

| 场景 | 优化前 | 现在 | 变化 |
|---|---|---|---|
| 标题页 | 29.0 fps（换库后） / 14.8 fps（原始） | **37.4 fps** | +29% |
| 游戏内大地图/客栈 | 13.8~16.4 fps | **20.6~21.1 fps** | +40% |
| 读档列表界面 | 约 12 fps | 约 12 fps | 不变（该界面本身重绘量大） |

## 一、SDL2 库：三条候选的实测

基准程序 `sdl2src/b3.c`（SDL dummy 视频驱动，源 1280×720 32bpp，`SDL_BlitSurface`，20 次取均值）：

| 库 | 大小 | full 1280→1280 | 320×180 | scaled 960×540 |
|---|---|---|---|---|
| `/usr/lib/libSDL2-2.0.so.0.12.0`（设备自带，**在用**） | 4,965,488 | **5.34 ms** | **0.33 ms** | **3.35 ms** |
| 设备原生编译 2.0.12（`-O3 -march=armv8-a -mtune=cortex-a53`，带 ALSA/udev/dbus） | 1,432,240 | 5.80 ms | 0.35 ms | 3.61 ms |
| `/usr/lib/aarch64-linux-gnu/libSDL2-2.0.so.0.2800.5`（系统默认 2.28.5） | 2,764,840 | 21.16 ms | 1.35 ms | 12.48 ms |

**读法：**

1. 2.0.12 确实比 2.28.5 快约 4 倍（这是之前"换库后 14.8 → 29 fps"的根源，方向正确）。
2. **自编译的 -O3 版反而慢 8%**（5.80 对 5.34）。原因不是编译质量，而是 SDL 的 blit 内层本就做了成熟的手写优化，`-O3 -mtune` 只会让代码变大、加重 i-cache 压力。→ **这条路线到顶，不要再折腾自编译 SDL2。**
3. 早期记录的 62.39 / 259.x ms 与本次绝对值不同（当时测试条件不同，可能含格式转换或带负载），但**4 倍的比例关系一致**，不影响结论。

## 二、缩放热点：从通用盒式滤波到 NEON

### 问题定位

`JY_FbBlit` 的缩小分支（通用盒式滤波）对每个输出像素跑双层循环累加 R/G/B，再查 `recip[9]` 表并移位拼接。1280×720 → 640×360 时每输出像素平均 4 个源像素，共 921,600 次像素读 + 每像素约 20~30 条整数指令。这一层实测占每帧约 8~11 ms（present 计时 `avg_ms=11.70`）。

### 做法

`patch_scale2x.py` 在 `sdlfun.c` 中插入一条**精确 2:1 缩小路径**（触发条件 `g_FbBytes==4 && srcW==dstW*2 && srcH==dstH*2`，正好覆盖 1280×720→640×360），每轮用 3 条 NEON 指令产出 2 个输出像素：

```
vld1q_u8 × 2        // 读源两行各 4 个像素
vhaddq_u8           // 垂直逐字节平均 (a+b+1)>>1
vuzp_u32            // 分离偶/奇像素 → [p0,p2] 与 [p1,p3]
vhadd_u8            // 水平平均 → 2 个输出像素
vst1_u32            // 写 2 个输出像素
```

- 误差上限 1 个色阶（两次 `(a+b+1)>>1` 的舍入），视觉上无差异，真机抓帧确认文字/立绘/地图无偏色。
- 输出宽度为奇数时末尾 1 像素回落到原 C 公式。
- 补丁幂等（源码内带 `JY_FB_SCALE2X_NEON` 标记，重复执行只会打印 `ALREADY_PATCHED`）。

### 遗留

`JY_FbStoreRow` 在 32bpp 下就是 `memcpy`，不是热点。放大路径（最近邻）与 960×540 等非整数比缩小仍走原逻辑，未改造。

## 三、否决项（有实测依据，勿再试）

| 方案 | 否决理由 |
|---|---|
| 自编译 SDL2 2.0.12（-O3 -mtune cortex-a53，设备原生） | blit 5.80 vs 5.34 ms，**更慢**；带 ALSA 动态加载版本还多 16KB |
| 云主机交叉编译 SDL2（1,416,424 B，无 ALSA） | 同上，且缺 ALSA 会改变音频路径行为 |
| 引擎 `-O3 -mcpu=cortex-a53` 重编 | 标题页 37.4（等于 O2）、游戏内 21.1（对 20.6，噪声内）；老代码对严格别名敏感，不值得为 2% 冒 UB 风险 |
| 降内部渲染面到 960×540 | 已验过会裁掉标题页右侧诗词；且瓶颈不在像素量 |

## 四、复现步骤（设备在线时）

引擎日志走两份：`/roms/ports/jysdlbh/fbdev.txt`（fbdev 后端 + 音频 diag，最可靠）、`/tmp/jysdlbh.log`（stdout，需 `stdbuf -oL` 才实时，launch.sh 已改）。

## 五、剩余瓶颈（下一步要动就得越界）

游戏内 20.6 fps ≈ 48.5 ms/帧。其中：
- NEON 缩放 + 写 fb：约 2 ms（原来 8~11 ms）
- 满屏 SDL 表面 blit：约 5.3 ms（若每帧一次）
- 其余约 40 ms 在引擎内部：图块/精灵绘制、字体渲染、Lua 逻辑

要继续往上，只能改引擎内部（违反"先不要动它的引擎"约束）。在现有约束下，本机这条链路已基本到顶。

# 追加：每帧到底花在哪（LD_PRELOAD 探针实测）

承接上文"剩余 40 ms 在引擎内部"只是帧预算倒推的说法。这一节是实测。

**方法**：`sdl2src/prof.c` hook `SDL_UpperBlit / SDL_UpperBlitScaled / SDL_FillRect / SDL_LockSurface / SDL_UnlockSurface / SDL_UpdateWindowSurface / SDL_PollEvent`，用 `LD_PRELOAD` 注入，**不修改引擎**。每 3 秒把累计计数与耗时覆盖写入 `/tmp/jyprof.txt`。其中 `LockedSegment` 记录 `LockSurface → UnlockSurface` 之间的墙钟时间，用来抓"引擎自己手写像素"的量。

坑：`LD_PRELOAD` 与 launch.sh 里的 `stdbuf -oL` 同时用会让进程被 SIGKILL（日志只留一行 `Killed`），探针期间必须去掉 stdbuf，直接 `LD_PRELOAD=... ./jysdllua`。

## 结果（32bpp 正式环境，增量分段统计）

| 场景 | fps | 帧预算 | UpperBlit 次数/帧 | blit 耗时/帧 | 占帧时间 | FillRect/帧 | 其余 |
|---|---|---|---|---|---|---|---|
| 标题页 | 37.4 | 26.7 ms | 17 | 9.9 ms | 37% | 1.4 ms | ~14 ms |
| 读档列表 | 12 | 83 ms | 49 | 56.7 ms | 68% | 4.9 ms | ~20 ms |
| 游戏内（客栈/大地图） | 20.8 | 48.1 ms | **1405** | **23.0 ms** | **48%** | 1.4 ms | ~22 ms |

单次 blit 成本：标题页 0.585 ms、列表 0.78 ms、游戏内 **0.016 ms** —— 游戏内每次都是一个 16×16 / 32×32 的小图块，**固定开销（格式检查、clip 计算、函数分发）远大于真正的像素拷贝**。

`LockedSegment` 全程 81.6 ms / 152 s，占 0.05% —— 引擎几乎不用 `LockSurface` 手写像素，绘制几乎全部走 `SDL_BlitSurface`。`SDL_PollEvent` 也在噪声内（0.05~0.16 ms/次）。

## 结论

这个引擎**每帧把所有图层从零重画一遍，没有任何脏矩形或图层缓存**。三处场景的 blit 总像素量都远超一屏（游戏内 1405 个小图块 ≈ 好几屏面积），属于典型的重复绘制。

也就是说：读档列表那个 12 fps 并不是"界面本身画得多所以救不了"，而是 49 次 blit / 帧占掉了 68%；游戏内的 48% 也是同一件事。**瓶颈是 blit 的"次数 × 固定开销"，不是 SDL 的像素拷贝速度** —— 这也解释了为什么换更快 / 自编译 SDL2 都没有收益：单次 0.016 ms 里几乎没有可优化的拷贝部分。

## 改造工程量（如果开这个口子）

统一的改法只有一种：**把不变的绘制结果缓存成 surface，只重绘变化的部分**。

| 目标 | 现状 | 做法 | 预期收益 | 风险 |
|---|---|---|---|---|
| 游戏内地图图块层 | 1405 次小 blit / 23 ms | 静态图块预合成到缓存 surface，滚动 / 换屏 / 动画图块变化时重建 | 23 → 约 5 ms，游戏内 **20.8 → 28~32 fps** | 滚动边界、动画图块（水面/火焰）要排除；易出错位 |
| 读档列表 | 49 次 / 56.7 ms | 列表项渲染结果缓存，只重绘光标 | 56.7 → 约 10 ms，**12 → 25~30 fps** | 列表内容变化（读档后）要失效缓存 |
| 标题页 | 17 次 / 9.9 ms | 背景 / 匾额等静态层缓存 | 9.9 → 约 3 ms，**37.4 → 43~45 fps** | 低 |

工作量（按游戏内地图这条最值钱的估）：
- 定位绘制循环（`mainmap.c` / `piccache.c`，需读实际代码确认入口）：1~2 小时
- 实现缓存 + 失效逻辑：2~4 小时
- 多场景回归（地图 / 战斗 / 菜单 / 过场）：2~3 小时

合计约 **1 个工作日**，收益游戏内 +8~11 fps、列表翻倍。

剩下约 22 ms 的 Lua/C 逻辑（脚本执行、地图计算）**没有采样工具**：设备无 `perf`、无 `gdb`，只有 `objdump` / `nm`（引擎未 strip，1,384 个符号）。要量化必须重编一版带分段计时的引擎，属于第二批工程。

## 已实施：场景层缓存（SMap / MMap）

profile 结论落地成两条补丁，都只包住"画静态场景层"这一个函数，引擎其余逻辑一行未动。

### 入口与做法

`mainmap.c` 里场景绘制有两处，都是每帧按菱形网格从零重画：

| 函数 | 场景 | 每帧循环 |
|---|---|---|
| `JY_DrawSMap` | 客栈、城镇等室内/小场景 | 第一遍地面层 `JY_GetS(..,0)`→`JY_LoadPic`，第二遍建筑层 `d1/d2` + 事件层 `d3` + 主角 `Mypic*2` |
| `JY_DrawMMap` | 大地图 | `BuildingSort` 后排 `Build[]`，逐格 `JY_LoadPic` |

补丁把原函数改名为 `*_raw`，在原位置前插一个同名包装函数：

- 缓存键：SMap 8 个（`sceneid / x / y / xoff / yoff / Mypic / clip.x / clip.y`，另比 `clip.w/h`）；MMap 7 个（`x / y / Mypic / clip.x / clip.y / clip.w / clip.h`）
- 命中：`SDL_BlitSurface(缓存, NULL, g_Surface, &clip)` 一次满屏贴，直接返回
- 未命中：调 `*_raw` 画到 `g_Surface`，再把 `clip_rect` 区域抄进一张 32bpp 缓存 surface（用 `g_Surface->format` 的 R/G/B/A mask 建面）
- 屏幕旋转（`g_Rotate != 0`）一律回落 raw，不缓存

补丁脚本：`patch_smapcache.py`、`patch_mmapcache.py`（纯 ASCII、幂等，源文件里留 `JY_SMAP_CACHE` / `JY_MMAP_CACHE` 标记）。

`Build[]` / `BuildingSort` / `BuildNumber` 已确认只在 `mainmap.c` 内部被 `JY_DrawMMap` 消费，没有外部依赖，所以命中缓存跳过它们不影响别的逻辑。

### 实测（真机 640×480 / 32bpp / stride 2560）

| 场景 | 缓存前 | 缓存后 | 备注 |
|---|---|---|---|
| 标题页 | 37.4 fps | **37.4 fps** | 该场景不走这两个函数 |
| 游戏内（客栈，静止） | 20.8 fps | **29.8~30 fps** | hb 增量 149/5 s |
| 游戏内（客栈，走动） | — | 26~27 fps | 走动时每步重建缓存，属正常 |
| 大地图（静止） | 未单独测过 | **26.0~26.4 fps** | hb 增量 130~132/5 s；图块与地名标签比客栈多，比客栈低约 4 fps |
| 大地图（走动） | — | 23.6~26.2 fps | 滚动时每帧重建缓存 |

帧预算从 48.1 ms 降到 33.6 ms，正好吃掉 profile 里那 23 ms 的 blit 时间。

画面核对：进出客栈、四方向走动、朝向、坐标显示、NPC 与水池火焰全部正常，抓帧无错位、无花屏。

### 编译参数与体积

缓存代码约 100 行。`-O2` 下引擎从 467,448 B 涨到 **471,968 B**（+4.5 KB），md5 `38fecfb4a7fa37eeb573ad6c40f070fa`。

中途踩过一次坑：设备上 `/tmp/tsjbuild/build/build.sh` 还是上一轮试验留下的 `-O3 -mcpu=cortex-a53 -fomit-frame-pointer`，用它编出的 519,832 B 版本比无缓存版大 52 KB，明显异常。同步回 `-O2` 后体积正常，且两版实测帧率相同（标题 37.4、客栈 29.8），说明此前"O3 无收益"的结论在缓存版上依然成立。

### 大地图实测

走出客栈进大地图后实测：静止 26.0~26.4 fps（hb 增量 130~132/5 s），滚动走动 23.6~26.2 fps。画面核对：坐标 363,238 → 363,241 向南三步，视角正确下移，上方涌入新地形（小村建筑、水塘、树丛），"福威镖局"地名标签随镜头滚动，无错位、无图块缺失、无花屏。

大地图比客栈低约 4 fps，原因是世界地图的图块与地名标签数量更多，命中缓存后仍要多贴一层。这一项在优化前没有单独测过基线，不能给出前后对比；按客栈 20.8→29.8 的同比例估算，移动前大约在 18 fps 上下。

回退方式（若后续出现异常）：设备上 `/roms/ports/jysdlbh/jysdllua.o2`（467,448 B，无缓存版）。
